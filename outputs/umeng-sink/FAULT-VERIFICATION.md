# 自建上报链路故障验证（2026-10-16）

## 隔离自动验证

在本目录运行 `npm run verify:failure`。脚本在随机临时本地端口启动真实接收端，将当前本地 H5 SDK 的导航模块装入隔离浏览器环境，通过真实 HTTP 客户端依次验证：正常接收、模拟断网（fetch 拒绝）、HTTP 503、接收端停服、原端口/归档目录重启及新页面恢复上报。业务回调在各阶段独立执行。脚本只读 H5 SDK，不接触 8787 或生产归档，退出时清理临时数据；需要允许绑定本地端口。可传 `--navigation-module /absolute/path/to/navigation.js` 指向另一个本地版本。

当前结果：失败时 H5 SDK 只告警，不会阻塞业务；恢复后**新**导航可上传。断网和停服期间已失败的导航不会补发；H5 目前无失败上传重试/跨进程持久化队列。接收端重启不会恢复客户端从未成功发送的事件。该脚本没有真实 iOS 运行环境，不得用于宣称真机原生上报已验证。此轮不验证友盟官方平台送达。

## 真机验证清单（需操作人员执行，不使用正式看板端口）

1. 使用单独测试端口、单独归档目录启动接收端，并以电脑局域网 IP 暴露给测试手机。仅测试构建将 iOS `AXXTelemetry.baseURL` 和 H5 `endpoint` 指向该端口；设置 `AXXTelemetry.debugLoggingEnabled=YES`；**不要修改官方友盟配置、域名、AppKey 或采样设置**。记录测试 App 版本、页面 URL、设备时间、测试端口及测试开始时接收端计数。
2. 正常联网进入内嵌 H5，验证业务页面可用，出现 `[AXX Telemetry] upload succeeded`，以及 H5 `[AXX Umeng] embedded navigation uploaded`；分别检查 `ios-context` 和 `h5-navigation` 新记录以及关联 ID。记录自建接收端对应时间窗口的 iOS 原生事件与 H5 导航事件；两类事件应分别核对。
3. 保持互联网通畅，**仅关闭隔离接收端**；重新进入 H5、前后台切换，确认业务正常，H5 出现 `upload failed`，iOS 最终出现 `upload failed`（默认 5 次重试，须等待超时和退避完成）。不要关闭 8787；此阶段只验证自建接收端不可用时业务仍可运行，不检查友盟后台。
4. 恢复隔离接收端，重新进入 H5、触发新的 iOS 原生事件；核对**新**事件进入看板。观察尚在同一进程、重试未耗尽的 iOS 事件是否补发；耗尽后不可假定补发。
5. 再次停止隔离端，强制结束 App 进程并重启，再恢复接收端。检查新会话与新导航关联，记录停服期间旧事件是否缺失：当前 iOS/H5 均无跨进程持久队列，旧事件丢失属于已知限制，不应标记为“可恢复”。
6. 最后单独测试关闭 Wi-Fi/蜂窝的全断网（使用本地可访问的缓存页面或已打开页面验证业务，不能把网页无法加载归咎于遥测）；恢复网络再次产生新事件。此阶段只验证自建链路不会令业务额外中断，并检查联网恢复后**新产生的**自建上报是否到达接收端；不检查友盟后台。

## 判定与边界

- 静态源码中官方 `AXXUmengSampled` 初始化和自建 `AXXTelemetrySDK` 初始化分离；原生自建上传使用独立 `NSURLSession`，网络错误、408/429/5xx 有限重试。保留官方集成但本轮不验证其平台送达，也不把官方后台无样本归因于自建链路。
- 真机需保存自建 SDK 的 `start result`、`upload succeeded/failed`、接收端各渠道原始事件计数与页面状态，区分“尝试发送”、“服务端接收”和“看板展示”；不要求官方后台出现样本。
- 全断网不能保证需要网络的业务请求继续成功；验收标准是自建上报失败不额外造成业务崩溃或阻塞、恢复后新事件可以到达自建接收端。
- 当前自建 iOS SDK 的原生事件不等于友盟全量崩溃、卡顿、OOM 原始数据；MetricKit 的诊断可能延迟交付。不要把本轮故障测试当作这些指标采集完整性的证明。
